## 一、邮件报告系统设计

分析报告的价值不仅在于平台内查看，更在于能及时送达用户手中。今天的第一项任务就是搭建邮件报告系统，让分析完成后自动生成精美的HTML报告并通过邮件发送给用户。

在此之前系统已有基础的邮件发送能力（`email_service.py`），但缺少报告内容的组装逻辑。我新建了 `backend/service/report_service.py`（354行），作为整个邮件报告体系的核心模块，统一负责三大职责：查询分析数据、生成HTML格式的报告正文、调用邮件服务发送。

## 二、HTML报告配色——与网站视觉统一

邮件报告的视觉设计是一个容易被忽视但实际很重要的环节。如果报告邮件的配色与平台整体风格不一致，用户会产生割裂感。平台采用的是暗色系 + 橙色/青色强调的扁平风格，我决定让邮件报告也遵循同一套设计语言。

整体布局采用 600px 宽度的居中卡片式结构，奶油底色 `#F8F2E4` 作为邮件背景，黑色卡片承载内容区域，顶部橙色 `#FF7A22` 横幅作为标题区。数据指标用大号橙色数字突出显示，情感分布用三色进度条直观呈现（青色正面、灰色中性、橙色负面）。

报告内容分为几个层次：首先是视频基本信息（标题、作者、平台、链接），然后是数据概览（评论总数、话题数量、情感占比），接着是各话题卡片（名称、评论数、占比、关键词、摘要），最后是AI综合分析段落。每个话题卡片采用奶油底 + 橙色边框的嵌套卡片样式，视觉层次清晰。

除了 Python 侧用代码拼接 HTML（更灵活地控制样式），我也建了一个 Jinja2 模板文件 `backend/templates/report_email.html` 作为备用方案，方便后续如果改用模板引擎可以快速切换。

## 三、修复LLM JSON截断——分析流程的"最后一公里"问题

前段时间 LLM 分析功能上线后，偶尔会出现分析任务完成但话题数据为空的情况。排查日志后发现是 DeepSeek 返回的 JSON 被截断了——当评论数量较多时，LLM 需要输出大量嵌套 JSON 结构，而之前的 `max_tokens` 设得偏保守（默认值），导致输出被中途截断，`json.loads()` 解析失败后整个分析结果被丢弃。

这其实是一个"最后一公里"问题：LLM 成功理解了所有评论，生成了高质量的分析内容，但因为输出通道不够宽，内容没能完整抵达。如果直接丢弃就太可惜了。

我的解决方案分两层。第一层是**预防**：将 `max_tokens` 显式设为 16384，确保绝大多数场景下有足够的输出空间，同时将 `response_format` 设为 `{"type": "json_object"}` 让模型更高效地组织 JSON 结构。第二层是**修复**：新增 `_try_repair_json()` 函数，当 `json.loads()` 抛出 `JSONDecodeError` 时不是直接放弃，而是尝试抢救。

修复逻辑的核心思路是：找到已输出内容的最后一个有效闭合位置（`]` 或 `}`），从此处截断，然后计算缺失的 `}` 和 `]` 数量并补全。虽然截断后的 JSON 不完整，但至少能保留已生成完成的话题，相比全部丢弃是一个巨大的提升。修复成功后日志会记录"JSON 修复成功 (截断补全)"和实际恢复的话题数量。

函数还有一个保底判断：修复后的结果至少要包含 `topics` 或 `overall_summary` 字段才被采纳，避免把完全乱码的内容当作有效结果。

## 四、设置接口与结果页面完善

在搭建报告系统的同时，也顺手完善了设置相关的后端接口和结果页面的展示逻辑。`backend/api/settings.py` 新增了对报告间隔等字段的支持，`backend/models/user_settings.py` 新增了 `report_interval_minutes` 字段用于控制追踪报告的发送频率。

结果页面（`results.html`）增加了报告发送功能的入口，用户可以在分析完成后手动触发报告发送。同时修复了分析流程中的几个边界问题，比如任务完成后状态更新不及时、结果页数据加载时序等问题。

## 五、小结

今天的核心成果是搭建了完整的邮件报告体系——从数据查询到HTML生成再到邮件发送的全链路。配色与网站保持统一，用户收到的报告具有良好的视觉一致性。更重要的是修复了 LLM JSON 截断这个生产环境中的实际问题，通过"预防+修复"两层策略大幅降低了分析结果丢失的概率。这个问题的解决思路也让我体会到：调用大模型时不能假设它的输出总是完美的，需要在工程层面做好容错设计。

接下来还需要让报告系统支持追踪模式下的周期性发送——不是一次性报告，而是每隔一段时间自动推送更新。
